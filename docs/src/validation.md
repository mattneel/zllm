# Validation

zllm aims to generate tokens as fast and accurately as the supported
hardware allows. Speed changes must preserve the intended computation, or
make a precision tradeoff explicit and measure its effect. Validation
therefore has several layers: file and text parity, individual kernels
against CPU computations, whole models against the CPU reference and an
external runtime, and stateful generation checks.

The commands below exit 0 when their gates pass. Results in this chapter
are recorded observations on the named models, inputs and backends, not
new runs of the current checkout or proof for all prompts and GPUs.
Fixture pins make comparisons reproducible; they do not make finite
coverage universal.

## Reading the accuracy results

- **Exact parity:** tokenization, prompt bytes, dequantization, selected
  cache encodings, and within-path step splits have exact-equality gates.
- **Numerical parity:** floating-point reductions can round differently.
  Kernel and model checks bound the resulting error instead of treating
  every different bit as a bug.
- **Model behavior:** top-1 agreement reports whether teacher-forced
  positions choose the same next token. Cosine, norm error and relative
  L2 also examine the activations, catching errors that argmax alone misses.
  The Gyro-Coder additionally requires identical expert choices.
- **Quality versus speed:** quantized weights, 8-bit prefill operands and
  FP8 KV are different tradeoffs. Comparisons use the same stored weights
  and, where necessary, emulate activation rounding to separate that
  tradeoff from an implementation error. These checks are not a general
  task-quality benchmark or proof of equivalent generated answers.

The automatic model-quality-gated [precision ladder](precision.md) is a
design target, not a completed load-time selector. f16 KV remains the
default; explicit FP8 support does not mean that FP8 has passed a model's
default-quality gate.

## Running the checks

```sh
scripts/fixtures.sh          # default fixtures, including dense models; model27b is separate
zig build test               # unit tests, no fixtures needed
zig build check-gguf         # GGUF reader vs llama.cpp gguf-dump
zig build check-tokenizer    # tokenizer vs Hugging Face
zig build check-chat         # chat prompts vs the Jinja chat template
zig build check-forward      # CPU f32 reference vs llama.cpp
zig build gpu-check          # every GPU kernel vs a CPU computation
zig build check-gpu          # GPU forward pass vs the CPU reference, step splits, engine
zig build check-dequant      # CPU dequantization vs ggml, bit for bit
zig build check-quant        # the quantized 27B: GPU vs reference vs llama.cpp
zig build check-gyro -Dgyro-model=<gguf>   # the Gyro-Coder: GPU vs reference vs its runtime
```

The Gyro-Coder is read in place from the supplied path; `fixtures.sh` has
no Gyro-Coder download target. The 27B fixture is optional and fetched with
`scripts/fixtures.sh model27b`.

Add `-Dgpu-host=d3d12` (Dawn WebGPU on D3D12) or
`-Dgpu-host=agility` (native D3D12/HLSL) to any GPU check
(`gpu-check`, `check-gpu`, `check-quant`, `check-gyro`, `check-fast`) to run
it on the Windows GPU from WSL; see [Backends](backends.md). The default
`native` host uses this build and Dawn's available adapter.

The backend is a test parameter, not a reason to weaken the reference or
tolerances. Every backend's kernel implementation is checked against CPU
reference computations through the same `gpu-check` cases; whole-model
gates run on the selected host as well. A missing kernel is reported as
`MISSING` and fails the kernel suite, rather than silently skipping it.
This is the validation contract for a backend, not evidence that every
available driver or adapter has already run every gate.

The checks need [uv](https://docs.astral.sh/uv/). It runs the harness in
`tools/` from its lockfile. `-Dfixtures=<dir>` points the checks at another
fixture directory. The reference forward pass uses one thread per physical
core; set `ZLLM_THREADS` to override that.

Two things keep the checks fast. Neither changes what they compare.

- **Cached references:** the CPU reference runs (`zllm forward`) and
  llama.cpp's dumps depend only on the model, the token ids and the code
  that produces them, never on the GPU kernels. They are cached in
  `.fixtures/cache`, keyed by:
  - the model file (path, size, modification time);
  - the token ids;
  - for the reference, a hash of `src/ref`, `src/gguf`, `src/graph`,
    `src/main.zig` and the build files;
  - for llama.cpp, its revision and the dump tool.
- **One load per model:** `zllm gpu-forward <model> --runs <file>` loads the
  model once for every run a check makes: chunk sizes, kernel paths, KV
  formats, fusion. Each run builds its own step program and frees it
  afterwards. On the Windows hosts the runs write their records (whole
  logits rows, hundreds of MB a run) next to the Windows stage, because a
  Windows process writes WSL's filesystem slowly.

The reference-cache and batching change was recorded in `a8abca4`
(2026-10-31): `check-gpu` on the RTX 5090 (D3D12) went from 28 minutes to
2.5 with the references cached. That is a harness-runtime measurement,
not an inference-speed result.

There are two tiers:

| Tier | What it runs | When |
|---|---|---|
| Fast: `zig build check-fast` | `gpu-check`; `check-gpu` on the first eval text (both kernel paths, step splits, every KV format) with engine-check; `check-gyro` on its short sequence (step splits and fusion bitwise) with `-Dgyro-model` | every iteration; about a minute on Agility once the references are cached |
| Full: every check | every eval text and model, the long prompts, `check-quant`, each backend | hardware validation before a commit; not all run in hosted CI |

`check-gpu` and `check-gyro` take `--fast` themselves; `check-fast` runs
them one after another, since the GPU runs one job at a time.

`-Dengine-check=false` skips the engine scenarios in `check-gpu` and
`check-fast`; the harness equivalent is `--no-engine-check`. The default
remains to run them. Hosted llvmpipe CI uses this opt-out, while the real
GPU checks on `d3d12` and `agility` keep the engine gate enabled.

The fast tier's approximate runtime was recorded in `c316cfc`
(2026-10-31). It is a shorter input set, not a replacement for the full
model gates.

### CI and hardware coverage

`.github/workflows/ci.yml` currently runs:

- Zig formatting and unit tests, and the wasm build;
- tokenizer and chat-template parity with pinned vocabulary fixtures;
- `zig build check-fast -Dengine-check=false` through Dawn on Mesa
  llvmpipe: `gpu-check`, then the first eval text through both model kernel
  paths, step splits and all KV formats against the CPU reference;
- TypeScript/Biome checks and the browser facade's unit tests;
- the mdBook and browser demo builds.

The GPU job restores the pinned model and vocabulary fixtures with
`actions/cache`, and separately restores `.fixtures/cache` for CPU
reference outputs. Its reference-cache key hashes `src/ref`, `src/gguf`,
`src/graph`, `src/main.zig`, the build files and `tools/corpus`; individual
reference entries also use the model and token ids as described above.

The hosted workflow skips `engine-check` on llvmpipe because of CPU cost
and the documented prefix-reuse rounding drift beyond its bound
([Engine](#engine)). It also does not run the full multi-model checks,
large-model forward checks, hardware soaks, Agility, or browser WebGPU
inference. Those need the corresponding fixtures and device. A green CI
run is therefore not a claim that every model/backend combination passed.

The detailed tables below mostly record Dawn D3D12 results on the RTX
5090 Laptop and selected llvmpipe results. Later backend evidence includes
`01b247e` (2026-10-30), which records every Agility kernel check and
engine scenario passing, and `823d6de` (2026-10-31), which records
`gpu-check` and Gyro-Coder split/fusion gates passing on both native
backends. These commits do not turn a Dawn-only table into a universal
cross-backend result.

## GGUF reader

`check-gguf` compares `zllm gguf-index` with `gguf_dump.py --json
--json-array` from the pinned checkout. It covers all 41 metadata keys in
order, with their types and values. Arrays (744,232 elements) are compared by
SHA-256 over the re-encoded elements. It also covers the names, types, shapes
and order of all 335 tensors. gguf-dump doesn't print the data layout, so the
alignment, data offset, and each tensor's absolute offset and byte size are
compared with the same checkout's `GGUFReader`.

## Tokenizer

`check-tokenizer` requires **100%** id equality with Hugging Face
`tokenizers` on `tools/corpus/tokenizer.jsonl`: 140 texts (7,860 tokens with
the 0.8B's tokenizer). It also requires identical decoded text. It runs on
the range-read GGUF header and on the full GGUF when present, for every
tokenizer zllm supports:

| `tokenizer.ggml.pre` | Model | Pre-tokenizer | NFC | `ignore_merges` |
|---|---|---|---|---|
| `qwen35` | Qwen 3.5 0.8B | Qwen 3.5 regex: marks join letter runs | yes | no |
| `qwen2` | Qwen 3 0.6B | the same without marks; one digit a piece | yes | no |
| `llama-bpe` | Llama 3.2 1B | Llama 3 regex: up to three digits a piece | no | yes |
| `granite-docling` | Granite 4.2 3B | GPT-2 regex | no | no |

The normalizer and `ignore_merges` come from each model's `tokenizer.json`;
GGUF does not record them, so zllm keys them on the pre-tokenizer. Each
column is load-bearing. NFC breaks 10 texts each for Llama 3 and Granite.
Merging Llama 3's whole-token pieces breaks 2, and one-digit pieces break 17.
GPT-2 breaks 20 texts without `\s+(?!\S)` and 2 with case-insensitive
contractions. See `tools/corpus/README.md` for what the corpus covers.

A corpus match is a release gate, not proof of equivalence. During
development, 3,000 randomly generated mixed-script strings also matched with
zero mismatches. That fuzz run is not a pinned check.

## Chat template

`check-chat` renders the 44 conversations in `tools/corpus/chat.jsonl` with
`zllm chat-render` (`src/chat/chat.zig`) and with the pinned Jinja template,
set up as Hugging Face `transformers` sets it up for
`apply_chat_template`. Every prompt must match byte for byte. The corpus
covers:

- merged and late system messages;
- every thinking tag and `reasoning_effort` value;
- reasoning inside replies, in tag variants, and passed separately;
- `preserve_thinking` off;
- Unicode whitespace trimming;
- a conversation past the template's 50-message rule;
- tools offered with and without a system prompt, thinking and an effort
  tag; calls with and without text before them, several per turn, and
  with non-string arguments (numbers, nested objects, arrays, null,
  non-ASCII and escaped characters); grouped tool responses; the
  template's tool-error warnings, including responses that look like
  errors but read as code or command output; and a multi-step
  conversation with no real user query.

The browser's tool-call parser has unit tests (`bun run test` in `web/`):
schema conversion, streaming in any chunking, partial tags and calls that
don't parse.

Joining merged system messages with one newline instead of two fails it.

The other models chat in their own GGUF template (`tokenizer.chat_template`),
which zllm renders with its Jinja interpreter (`src/chat/jinja.zig`).
`check-chat` renders the same 44 conversations with each dense model's
template, through zllm and through jinja2 set up as transformers sets it up
(its `tojson`, `raise_exception` and `strftime_now`, the clock fixed on both
sides), and requires byte-identical prompts, or both refusing:

| Template | Match | Refused by both |
|---|---|---|
| Qwen3-0.6B | 44 | 0 |
| Llama-3.2-1B-Instruct | 43 | 1 (more than one tool call in a turn) |
| Granite 4.2 3B | 44 | 0 |

Dropping `trim_blocks`' newline fails all 44 of Granite's, dropping
`lstrip_blocks` 23, `tojson` without its space after commas 20 across the
three, and strings not counting as iterable 6 of Llama's. The interpreter's
unit tests pin the rest of its Python semantics: `str()` of values, floor
division, code-point indexing and slicing, scopes, macros.

## Reference forward pass

`check-forward` runs `zllm forward` and `llama-dump`
(`tools/llama-dump/dump.cpp`, linked against the pinned libllama) on the same
token ids: teacher-forced, one batch, starting from an empty state. The ids
come from tokenizing `tools/corpus/eval.jsonl` (5 texts) with each model's
pinned Hugging Face tokenizer. llama.cpp runs with an f32 KV cache and
flash attention off. It runs on the 0.8B and on the dense models
([Dense models](#dense-models)).

Pass criteria:

| Metric | Threshold | Scope |
|---|---|---|
| Top-1 token agreement (argmax of logits) | ≥ 99% | all positions |
| Final hidden state (`result_norm`) cosine similarity | ≥ 0.999 | every position |
| Final hidden state norm error, \\(\lvert \lVert z \rVert / \lVert r \rVert - 1 \rvert\\) | ≤ 1% | every position |
| Each layer's relative L2 error, median over a sequence's positions | ≤ 1e-2 | every layer and sequence |

Cosine similarity can't see scale errors, so the norm-error bound covers them.
The per-position bounds catch an error at any position; the median bound
catches an error in the graph, which moves most positions, where a few
positions amplify rounding differences (Granite, below). The check prints,
for every layer output, the minimum and mean cosine, the maximum and median
relative L2 error and the maximum norm error. It also writes them to
`.fixtures/reports/forward.json` (`forward-<name>.json` for the dense
models).

Results for the 0.8B at the pins above (worst layer median 4.7e-3):

| Sequence | Tokens | Top-1 agree | Final min cosine | Final max norm error |
|---|---|---|---|---|
| prose | 148 | 148 | 0.999974 | 9.8e-4 |
| chat | 131 | 131 | 0.999814 | 2.1e-3 |
| code | 243 | 242 | 0.999940 | 1.3e-3 |
| multilingual | 102 | 101 | 0.999961 | 5.7e-4 |
| math | 194 | 194 | 0.999964 | 8.5e-4 |
| **all** | **818** | **816 (99.76%)** | **0.999814** | **2.1e-3** |

The remaining differences are consistent with llama.cpp's CPU BF16 matrix
multiply, which converts f32 activations to BF16 before each dot product
(`vec_dot_type = GGML_TYPE_BF16` in `ggml-cpu.c`). The zllm reference keeps
activations in f32 and widens the BF16 weights to f32.

To show the check can fail, a deliberately wrong reference that drops the
attention output gate scores 2.4% top-1 and fails every position.

## GPU kernels

`zig build gpu-check` (`src/kernels/check.zig`) runs the kernel suite on
seeded random inputs. It compares each implementation against a float64
CPU computation of the same formula, or the sampler's CPU reference, with
shapes that hit tile and chunk remainders. The same suite selects WGSL
through Dawn or HLSL through Agility; passing against the other GPU
implementation alone is not the reference criterion.

Load-time tuning is a separate check: `src/tune/tune.zig` compares each
candidate quantized decode multiply against the default GPU variant on
real model weights before timing it, and drops diverging candidates.
It does not rerun the entire CPU-reference suite during each browser load
or substitute for model-quality validation.

Kernel cases include:

- **Stateful kernels** run as steps that carry state between them. The
  DeltaNet front end runs in steps of 5, 2, 1 and 4 tokens, with the delta
  rule advancing the conv history between them; steps shorter than the
  history shift it. The delta rule runs as two steps.
- **Attention** runs 70 query tokens after 270 cached positions as a
  prefill step runs them, in chunks of 32, 32 and 6 tokens over six
  64-position blocks, the last partial, with f32 and f16 caches, query
  rows padded past their gates as in the fused Q, K, V projection. Decode
  attention covers three query tokens over three blocks. Both run with
  groups of 4 query heads a KV head (`attn_split`) and 12
  (`attn_split_wide`).
- **Sparse attention** (Qwen3.8-Flash-Next): the indexer runs 230
  positions in steps of 3, 4, 1 and 2. Every query head of a token is the
  same, so about half the blocks score exactly 0, and rows just past the
  width must break those ties by index. The key cache and every row's
  selection must be exact, against the raw keys rounded and a sort of the
  GPU's own scores; the queries, pooled blocks and scores within 1e-5 of
  float64 (4.3e-6). `attn_split_sparse` runs with a whole 64-key block
  excluded, and with a width past every row, which attends to all, against
  float64 (2.6e-7). Ranking ties from an inclusive scan, taking the last
  block whole, rotating pooled blocks at the wrong position, and taking one
  cell too many each fail.
- **`rope_append`** is checked over the whole projection, including the
  gates, K and V it must leave untouched, and over the cache, including the
  positions before the step, which must stay zero. Its f16 cache must hold
  exactly its f32 cache's values rounded to nearest, ties to even, over
  random values at exponents −28 to 17 and planted ties, subnormals,
  overflow, ±inf and NaN. Two more cases run the dense models' layouts:
  query heads without gates, no Q/K norm and normal RoPE pairs with
  per-pair angle divisors (Llama, Granite), and Qwen 3's (Q/K norm, NeoX).
  Ignoring any of the three switches, or the divisors, fails them; the
  ungated attention cases fail with the gate applied or the gated query
  stride.
- **Fused multiplies** start from a random output, so an accumulate that
  overwrites fails.

The rows below are recorded RTX 5090 (Dawn D3D12) results. The documented
llvmpipe runs gave the same errors to within a factor of 2; neither row set
asserts coverage of every device.

| Kernel | Max relative error | Tolerance |
|---|---|---|
| rmsnorm | 1.6e-7 | 1e-6 |
| matmul_bf16 (single; 2-chunk accumulating), matmul_f16 | 1.3e-6 | 1e-5 |
| matvec_bf16 (2-chunk; 2-chunk with norm and accumulate; norm and SiLU pair), matvec_f16 (with norm and accumulate; SiLU pair), 3 tokens | 1.9e-7 | 1e-5 |
| silu_mul | 1.4e-7 | 1e-6 |
| embed_bf16, embed_f16 | 0 | 0 |

| rope_append, f16 cache | 2.4e-4 | 5e-4 (half an f16 step) |
| matvec q8_0 with the hc_act prologue (fused), every variant, inputs read from wider rows | 1.1e-7 | 1e-5 |

WGSL lets `pack2x16float` round either way: llvmpipe rounds to nearest,
D3D12 toward zero, half the values a step low, biasing every cached K and V
toward zero. `rope_append` rounds to nearest itself, as llama.cpp's cache
does. Truncation fails the rounding check on D3D12 (half the values
differ), as do ties rounded up, normal or subnormal. On the Gyro-Coder the
truncated cache had put the logits 3.7e-3 (median relative L2) from the
reference; rounded, 1.9e-5. Dropping the attention output gate
makes `gpu-check` fail with error 1.0. Mutations of the fused kernels each
fail their check:

- **Conv history:** shifting it one slot too far, or reading the wrong slot
  (errors 0.08 and 0.13).
- **Fused projections:** reading z or α at the wrong offset, or queries at the
  unfused row stride.
- **The SiLU pair's up row:** off by one.
- **The norm prologue:** a wrong mean divisor (k + 8; errors 4e-3 and 8e-3)
  or one weight for every element.
- **Accumulate:** overwriting instead of adding.
- **The V cache:** taking the rotated K.

The sampler runs on seeded Gaussian logits (σ = 2), so every threshold cuts
through a dense band of tokens:

- **Configurations:** each path through the sampler's phases. They cover
  greedy with penalties and bias; top-k 40 with top-p 0.9; min-p 0.05;
  top-p 0.5; plain T = 1; top-k 1; top-k 2,000 with top-p 0.8 (past the
  candidate cap, so top-p bisects); min-p leaving fewer than k tokens; and
  the full 248,320-token vocabulary with every control at once.
- **Each draw:** the stop flag, the next-step token and the count update
  must be right, and the token must be the CPU reference's draw up to
  rounding.

Exact equality would be the wrong bar. The GPU accumulates the inverse CDF
in f32 with its own `exp`, and with mass spread over 32k tokens a draw near
an interval boundary can land on the neighbour.

- **The criterion:** u must fall within 1e-6 of the kept mass of the GPU
  token's CDF interval, with the min-p and top-p cuts allowed to move by the
  same relative amount.
- **Greedy and top-k:** these compare bit-identical values and must match
  exactly.

| Host | Draws | Exact | Worst deviation |
|---|---|---|---|
| RTX 5090, D3D12 | 91 | 91 | 0 |
| llvmpipe, Vulkan | 91 | 91 | 0 |

On different seeded data, one plain T = 1 draw out of 16 picked the
neighbouring token, 4.4e-8 from its boundary. Mutations fail:

- **Min-p cut halved:** deviation 1.0, a token outside every plausible kept
  set.
- **Top-p cut halved:** deviations up to 0.3.
- **Off-by-one in the top-k radix select:** fails the three
  configurations where top-k cuts (k = 20, 40 and 2,000).

## Quantized weights

The 27B mixes Q3_K, Q4_K, Q5_K, Q6_K and Q8_0 weights. Three checks build
up to it:

- **Dequantization:** `check-dequant` decodes 4,096 random blocks of each
  type with zllm's CPU decoders and with the pinned llama.cpp build's
  `dequantize_row_*`, and requires bitwise equality. Every byte is random
  except the f16 super-scales, so every quant, scale and high-bit pattern
  occurs. All five types pass.
- **Kernels:** for each type, `gpu-check` runs the decode multiply with its
  norm prologue and accumulate epilogue, the prefill multiply accumulating
  (70 tokens × 150 outputs, whole and split over k through
  `matmul_reduce`), and the embedding gather against float64 over those
  decoders. Weights go through `Launcher.layout` (`repad`, `repack_q3_k`, `repack_q8_0`) as the loader's do. The prefill
  multiply's input is rounded by `quantize_q8`, and the float64 sum runs
  over the reference's rounding of it. Further checks run x over two
  staged tiles (k = 4,096) and the SiLU pair on Q3_K, the 27B's gate and
  up type, and `quantize_q8` against the reference's rounding, value for
  value, in both block formats. The rows include a negative largest
  value, a tie between +max and −max, and a zero block. Two more check
  it computing its input, RMSNorm and the SiLU pair, first: every value
  must be within half a step of the f64 result. The Q8_0 gather also
  runs over rows stored 172 bytes apart with junk between them, as the
  Gyro-Coder's PLE rows arrive. All 22 pass on
  llvmpipe and the RTX 5090: embeddings and rounding exactly, multiplies
  within 5.6e-7. The rounding needed exact division: WGSL's may be off by
  2.5 ULP, and on D3D12 that moved values across rounding boundaries.
- **The model:** `check-quant`, below.

The CPU reference cannot hold the 27B in f32 (108 GB). Quantized matrices
stay in the file mapping, and each thread of the reference multiply decodes
a 32-row panel just before using it. A 148-token sequence takes 8 s on 32
threads.

### The 27B

`check-quant` runs every eval sequence (818 positions) through the CPU
reference, through the reference with llama.cpp's activation rounding
emulated, through pinned llama.cpp, and through the GPU on both kernel
paths.

**GPU against the reference, decode kernels.** Both use the same decoded
weights and f32 activations:

| Kernel path | Top-1 | First layer, max rel L2 | Everything, max rel L2 |
|---|---|---|---|
| Decode (1-token steps, first 40 positions) | 200/200 | 2.9e-6 | 2.1e-5 |

The bounds are 1e-5 for the first layer (exact up to f32 summation order)
and 1e-3 everywhere, with cosine ≥ 0.99999. The second bound is looser than
the 0.8B's 1e-4 because the 27B amplifies small differences. At position 61
of the math sequence, the GPU–reference gap is 2e-7 through layer 15 like
every other position, then grows smoothly to 4.3e-4 by layer 63. A kernel
bug would instead show a step at the layer that uses the kernel.

**GPU against the reference, prefill kernels.** The quantized prefill
multiplies round their input to 8-bit blocks as llama.cpp does, so they
are compared with the reference that rounds the same way
(`--llama-activations`, below), by the bounds used for llama.cpp itself.
Rounding is discontinuous: the GPU's activations differ from the
reference's by f32 summation order, about 1e-7, and a value that close to a
rounding boundary rounds the other way, which moves a multiply's output by
about 5e-4. So a per-position bound can't hold, and the bounds take
medians over positions:

| 32-token steps, 818 positions | GPU | llama.cpp | Bound |
|---|---|---|---|
| First layer against the rounded reference, worst median rel L2 | 2.9e-5 | 3.4e-5 | 1e-4 |
| Gap to the f32 reference over its own gap to the rounded one, worst layer | 1.10 | 1.08 | 1.5 |
| Top-1 against the rounded reference (reported) | 805/818 | | |

Each kernel on that path, including the rounding, has its own CPU-reference
check in `gpu-check`: rounding is held exact, while multiplies have
floating-point error bounds.

**Reference against llama.cpp.** llama.cpp rounds each quantized
multiply's input to 8-bit blocks (Q8_K for the K-quants, Q8_0 for Q8_0);
the reference keeps f32. `zllm forward --llama-activations` applies the
same rounding, which separates the two causes of a difference:

| Layer | Reference vs llama.cpp | Reference vs itself with the rounding |
|---|---|---|
| 0 | 9.13e-3 | 9.13e-3 |
| 1 | 1.02e-2 | 1.02e-2 |
| 31 | 2.34e-2 | 2.30e-2 |
| 63 | 3.16e-2 | 3.00e-2 |

(Median relative L2 over positions; the prose sequence.) The reference's
response to llama.cpp's rounding matches its gap to llama.cpp at every
layer, in every sequence, within a factor of 1.08. With the rounding
emulated, the first layer agrees with llama.cpp to a median of 3.4e-5 or
better; only the emulation's rounding ties differ. A semantic difference,
such as a wrong head mapping or norm, would add a gap the rounding cannot
explain, from the first layer of the affected kind on. The bounds are 1e-4
and a factor of 1.5.

The spec's model bounds against llama.cpp (cosine ≥ 0.999 and top-1 ≥ 99%,
§12) are reported but not enforced for the 27B. llama.cpp's rounding alone
breaks them: the reference against its own rounded run agrees on 143 of 148
tokens of the prose sequence. Against llama.cpp it agrees on 800 of 818
(97.8%), with a worst final-state cosine of 0.342 at one position.

These are explicit exceptions to the draft spec's single model threshold,
not evidence that the spec's top-1 and cosine bars passed. The implemented
gate asks whether the numerical difference is explained by the measured
rounding path. It does not establish that rounding has no effect on
downstream task quality.

## GPU forward pass

`zig build check-gpu` runs `zllm forward` (the CPU reference) and
`zllm gpu-forward` on the same token ids for all 818 eval positions.
`gpu-forward` processes them as steps against the KV cache and the recurrent
state, as generation does, through either kernel path
([GPU backend](gpu.md#two-kernel-paths)). With an f32 cache, both use the
same BF16 weights and f32 activations, so they can differ only by reduction
order and the rounding of `exp` and similar functions. The bounds are
therefore tight:

| Run | Requirement | Scope |
|---|---|---|
| Prefill kernels, f32 cache, 512-token steps | 100% top-1 agreement; cosine ≥ 0.999999 and relative L2 ≤ 1e-4 | every layer output, final norm and logits, every position |
| Prefill kernels, 7-token steps | bitwise identical to 512-token steps | everything |
| Decode kernels, 1-token steps (as decoding runs), first 40 positions | the same bounds as 512-token steps | the same |
| Decode kernels, 3-token steps | bitwise identical to 1-token steps | everything |
| f16 cache (the default) | ≥ 99% top-1 agreement; cosine ≥ 0.99998 | top-1 aggregated over the texts/models selected for this invocation; cosine over every compared record and position in each run |
| FP8 cache (E4M3) | ≥ 95% top-1 agreement; cosine ≥ 0.975 | the same aggregation and per-run cosine scope |

A full invocation includes every eval text and each dense model's first
text; `--fast` uses only the first eval text and no dense models. KV top-1
is not gated separately per model or text. For example, the Qwen3 FP8 row
below is under 95% on its own, while the full aggregate passes. This is
another reason not to treat the aggregate path check as a model-specific
quality gate.

With a model that has an MTP block (the 0.8B fixture does), the f32-cache
runs also check the block's draft logits (`mtp_logits`, one row per
position but the last) to the same numerical bounds as the logits and
require 100% draft top-1 agreement. KV-format runs include these records
in their cosine check, but do not add a separate draft-top-1 gate.
On llvmpipe they agree to 7.5e-6 relative L2 on both kernel paths, and the
step splits stay bitwise identical. On the 27B in 64-token steps, the
quantized prefill puts them 2.3% (median) from the f32 reference, as it does
the logits.

RTX 5090 (D3D12):

| Kernels | Top-1 | Max relative L2 | Splits |
|---|---|---|---|
| Prefill | 818/818 | 1.2e-5 | bitwise identical |
| Decode | 200/200 | 1.1e-5 | bitwise identical |
| Prefill, f16 cache | 818/818 | min cosine 0.9999984 | |

Each fusion commit passed this check on its own.

The FP8 cache stores E4M3 (3 mantissa bits): each cached value carries up to
2^-4 relative rounding error. On the RTX 5090 (D3D12) it agrees on top-1
with the f32 reference on 1,231 of 1,264 positions over the eval texts and
the dense models' first:

| Model | f16 cache | FP8 cache | FP8 min cosine |
|---|---|---|---|
| Qwen3.5-0.8B (5 texts) | 818/818 | 806/818 | 0.984 |
| Qwen3-0.6B | 148/148 | 139/148 | 0.991 |
| Llama-3.2-1B | 149/149 | 144/149 | 0.982 |
| Granite 4.2 3B | 149/149 | 142/149 | 0.984 |

The FP8 bounds catch a broken cache path, not the quality a model needs.
`ecec4af` (2026-10-31) records 1,231/1,264 top-1 agreement on Dawn and
1,233/1,264 on Agility for this model/input set. These small models stay
on f16 by default; automatic selection under the spec's precision ladder
is not implemented. Choosing FP8 explicitly accepts a different accuracy
profile, even when its encoding and attention kernels pass their tests.

`gpu-check` holds the FP8 encoding itself exact: `rope_append`'s FP8 bytes
and power-of-two scales match `ref/fp8.zig`'s encoding of its f32 output
bit for bit, on every backend.

Earlier recorded llvmpipe model runs gave 818/818 top-1 and 1.0e-5
relative L2 before the decode kernels were added. The current workflow
uses the cached-reference fast tier to keep model-path coverage on
llvmpipe, rather than limiting CI to individual kernels. Full multi-model
and engine validation remain separate from that hosted subset.

Top-1 agreement alone is a weak check. Halving the RoPE base on the GPU
still agrees on 814 of 818 tokens, which would pass the 99% bar used against
llama.cpp, but it drives the per-layer relative L2 error to 6.3e-2, and
`check-gpu` fails.

## Engine

By default, `check-gpu` also runs `zllm engine-check`; the llvmpipe CI
invocation disables it explicitly. It sends requests through the
real engine after earlier requests left state behind. With an MTP block
(the 0.8B has one), they speculate, except the pipelined and cancelled
ones, so the reuse scenarios start from states that speculative rounds
left, rolled back or not. Then it repeats each
one after dropping all state. Each sampled step's logits must match, and the
reused prompt length must be what the reuse rules say. Logits must be
bitwise identical wherever both runs put each position through the same
kernels. Prefill chunks always run the prefill kernels, so that holds for
every scenario but one: a prompt that extends a turn reuses the reply's tokens,
which went through the decode kernels. That one must agree within 1e-4
relative L2.

| Scenario | Reused | Logits |
|---|---|---|
| A fresh 700-token prompt | 0 | bitwise identical |
| The prompt, its reply, and 40 more tokens | 711: the whole resident sequence | relative L2 4.5e-5 |
| A prompt sharing the first 600 tokens | 512: the checkpoint at 512 | bitwise identical |
| The same prompt again | 649: the checkpoint before its last token | bitwise identical |
| The first prompt after an unrelated one | 0: the state is zeroed | bitwise identical |
| The first prompt again, pipelined as in the browser and stopped by its 6th token | (fresh) | 6 tokens with bitwise identical logits to an unpipelined run; 706 resident, the stop token included |
| That prompt, its stopped reply, and 30 more tokens | 706 | relative L2 2.3e-5 |
| After a 300-token prompt cancelled after 3 tokens: it, those 3, and 30 more | 302: the prompt and the 2 processed tokens | relative L2 8.8e-5 |
| After a 700-token prompt cancelled after its first prefill step: the same prompt | 448: the chunk that ran | bitwise identical |
| Logprobs: a 300-token prompt, greedy, top 3 | (fresh) | each token's logprob within 1.2e-7 of the log-softmax of its read-back logits, the top entry the sampled token; identical without the check's readback |
| Speculation: a prompt repeating a random 24-token phrase, 48 tokens, greedy, sampled, and sampled with penalties, with and without speculation | (fresh) | the same tokens and bitwise identical logits; 52 drafts accepted and 34 rejected across the three |
| Device lost (forced): the 300-token prompt before and after | (fresh) | the request fails with `error.DeviceLost`; the runtime rebuilds with the plan cache's tuning (2.2 s); bitwise the tokens and logits of the run before. A rebuild that tunes again instead fails it |

The pipelined run completes each batch only when the engine asks for it
(`wait`), so every decode step is recorded before the previous token is
known, as in the browser ([Generation](generation.md#engine)). A program
that cannot chain samples (Qwen3.8-Flash-Next) keeps one batch in flight,
so no step processes the stop token: the scenario then wants it not
resident. The cancelled
decode's follow-up sits closest to the cross-path bound, at 8.8e-5 of 1e-4:
two of its reused positions went through the decode kernels.

These are recorded RTX 5090 results; the first five scenarios also passed
bitwise in earlier llvmpipe runs. Later, llvmpipe exposed a scheduling
dependency: the chunk just before a prompt's last token could be a tail of
fewer than 8 tokens, and timing noise decided whether it ran alone through
decode kernels or inside a longer prefill chunk. Prefill chunks now always
run the prefill kernels. The documented llvmpipe extended-turn result is
still 1.4e-4, past the 1e-4 bound; the historical RTX table above records
4.5e-5. This failed software-renderer gate, together with its CPU cost,
is why CI skips engine-check rather than loosening the bound. Engine
validation remains enabled on the real GPU backends.

Skipping the checkpoint restore fails both checkpoint scenarios, and an
earlier bug that left the state dirty after dropping the sequence
failed all five. Leaving the pipelined placeholder unfilled fails the
scenario after the pipelined stop (699 of 736 reused, want 706). Skipping
the rollback after a rejected draft, or drawing the next sample afresh
instead of with the rejected round's second draw, fails the sampled
speculation scenario; leaving the discarded sample counted fails the one
with penalties.

## Dense models

One model per dense architecture ([Dense transformers](dense.md)), each
BF16: Qwen3-0.6B, Llama-3.2-1B-Instruct and Granite 4.2 3B (pins above).
BF16 keeps llama.cpp's comparison continuous enough to bound position by
position. For quantized weights, llama.cpp rounds every multiply's input
to 8-bit blocks, and the 3B at Q4_K_M already differs by 4e-3 to 7e-3
(median) after its first layer: Q, K and V match to 8e-7, but a few rows
round across a step and attention spreads them to every later position.

**Reference against llama.cpp** (`check-forward`, 5 sequences each):

| Model | Positions | Top-1 | Final min cosine | Final max norm error | Worst layer median rel L2 |
|---|---|---|---|---|---|
| Qwen3-0.6B | 839 | 839 (100%) | 0.999760 | 9.5e-3 | 4.7e-3 |
| Llama-3.2-1B-Instruct | 839 | 831 (99.05%) | 0.999788 | 2.0e-3 | 6.7e-3 |
| Granite 4.2 3B | 890 | 889 (99.89%) | 0.990218 | 2.7e-2 | 5.6e-3 |

Granite's activations reach 14,840 in one dimension from layer 6, and a few
positions amplify llama.cpp's BF16 rounding of activations. Position 139
of the math sequence (a space token) tracks its neighbours at 2e-3 to 4e-3
through layer 9, then pulls away smoothly, to 0.15 by layer 33, while
position 138's error stays at 4e-3 and the median at 3e-3. Emulating
llama.cpp's rounding (`--llama-activations`) does not remove it. So
Granite's per-position bounds are cosine ≥ 0.99 and norm error ≤ 3%; the
median bound is everyone's.

Each switch is load-bearing:

- **No `rope_freqs` (Llama):** final cosine 0.9987 and 144 of 149 top-1 on
  prose, against 0.99997 and 148.
- **1/√d instead of `attention.scale` (Granite):** layer median 0.94, final
  cosine 0.18, 35 of 149 top-1.

**GPU against the reference** (`check-gpu`, the prose sequence of each, f32
cache): the 0.8B's bounds (cosine ≥ 0.999999, relative L2 ≤ 1e-4 at every
position and layer, every top-1), on the prefill kernels (one step) and on
the decode kernels (1-token steps, first 40 positions). Every dense model
passes on llvmpipe and on the RTX 5090 (D3D12); with the 0.8B's sequences,
the worst relative L2 is 1.7e-5 (llvmpipe) and 1.3e-5 (D3D12), and every
top-1 agrees (1,264 prefill and 320 decode positions). The GPU program
ignoring `rope_freqs` moves Llama's layers by 1.6e-2 within 24 tokens.

`zig build check-gyro -Dgyro-model=<gguf>` runs the GPU rows of this table
on the selected host. The prompts and greedy tokens are the reference
runtime's, kept in `tools/corpus/gyro_*.json`. It requires:

- the same experts as the CPU reference in every layer and position;
- streams within 1e-3 relative L2, and logits within 1e-4 (median) and 1e-3
  (max);
- every position's top-1 agreeing, which makes the greedy tokens the
  runtime's 40;
- one-token and four-token steps bitwise identical;

  layer's streams and experts and the logits (97 records; a fused prologue

wrong kernel: a routing flip moves a row by about 1e-2.

rounding: that runtime computes multiplies from activations rounded to
8-bit blocks, and the difference grows through the hyper-connected
streams. Unlike the rounded-reference comparison for the
[27B](#the-27b), this chapter does not report a matching rounded
Gyro-Coder reference that isolates the cause. The recorded routing and
greedy-token matches are narrower evidence than layer-by-layer numerical
equivalence to the external runtime.

## GPU safety

The spec's safety target is no submission over 250 ms and no device hang
in a soak test. `zllm soak <model.gguf> [minutes]` runs requests of varied
shapes through the engine: prompts of 1 to 3,000 random tokens, about half
extending the previous one (prefix reuse, checkpoint restores), greedy and
sampled, replies of 1 to 256 tokens, and cancellations. It times every
submission and fails on a device error or one past the cap. A finite soak
establishes behavior for that run, not immunity to hangs on every driver.

| Model, RTX 5090 Laptop (D3D12) | Minutes | Submissions | Max | p99 | Over 250 ms | Device errors |
|---|---|---|---|---|---|---|
| Qwen 3.5 0.8B BF16 | 2 | 15,861 | 155 ms | 123 ms | 0 | 0 |
| Qwen 3.8 27B Q3_K_M | 10 | 9,703 | 222 ms | 180 ms | 0 | 0 |

The first 27B soak failed twice over. Prefill attention grew with position
until 32-token steps at 5,000 positions took over 200 ms, now split over
blocks of cache positions. And a step of a few tokens, run by the decode
kernels, set the per-token rate a later chunk was sized by, making it
three tiles long (295 ms); such steps no longer set the rate. Long
contexts still bring 32-token steps near 220 ms.


In Chrome on the RTX 5090, greedy generation gives the same 256 tokens as
the native host, loaded both over HTTP and from a local file
([Browser](browser.md#validation)). The wasm build compiles in CI; the
WebGPU path runs only in a browser with a GPU.
